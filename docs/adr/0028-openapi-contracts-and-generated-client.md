# ADR 0028: The OpenAPI documents are committed contracts, and the client is generated from them

Status: Accepted (Week 4, Part C).

## Context

The tracking API needs:
- documentation for partners;
- a typed C# client;
- a way to see every change to the contract.

ASP.NET Core 10 generates OpenAPI documents itself. Swashbuckle offers a generator and a viewer, and NSwag and OpenAPI Generator can turn a document into a client. Running two generators would produce two descriptions of one API that can disagree.

## Decision

- **One generator: the built-in `Microsoft.AspNetCore.OpenApi`.** Swagger UI uses only Swashbuckle's viewer package (`Swashbuckle.AspNetCore.SwaggerUI`), pointed at the built-in documents. A test checks that SwaggerGen is not installed. The documents and Swagger UI are served in Development only. That is a choice about what to publish, not a security control.
- **The documents describe the HTTP contract, not the C# types.** The sources are XML comments (enforced by `GenerateDocumentationFile`, where a missing comment fails the build), `[EndpointSummary]`, `[Tags]`, `[ProducesResponseType]` for every status code, and route names as operation IDs. Small transformers correct the places where the CLR types would mislead a client:
  - enums travel as names in requests and in v2;
  - numbers are not strings, and decimals are `decimal`;
  - `[Required]` fields are never null;
  - a 201 has a `Location` header;
  - there is no host-specific `servers` list.
- **The documents are committed** as `contracts/v1.json` and `contracts/v2.json`. `contracts/export-contracts.ps1` writes them from the running API, and `ContractTests` fails when they differ from what the API serves. A contract change is therefore always a reviewed diff, classified in [VERSIONING.md](../../VERSIONING.md).
- **The C# client is generated by NSwag from `contracts/v2.json`,** not from the running API. The NSwag version is pinned in `dotnet-tools.json`, and the settings are in `src/ApexPost.Client/nswag.json`. The generated file is committed and never edited. Hand-written code goes in partial classes (`TryGetShipmentAsync`, `IsNotFound`) and wrappers (`AddApexPostClient`). Regenerating with the same contract and tool produces a byte-identical file.

## Consequences

- **The client and the documentation describe exactly the same contract,** the committed one. A client build needs neither the API nor NSwag.
- **Every change to a DTO or XML comment needs one extra step,** running the export script, or `ContractTests` fails. That friction is deliberate: it is where a breaking change gets noticed.
- **The transformers are ours to keep working with new .NET releases.** The OpenAPI tests check their output for both versions, and they were written after measuring what the generator produced, never from guesses.
- **The generated client depends on nothing but `Microsoft.Extensions.Http`.** Its exceptions (`ApexPostApiException<ProblemDetails>`) carry the API's ProblemDetails, so partners handle errors by status and type, not by parsing text.
